# Architecture

AeroSec Tower is a lightweight AI-powered DevSecOps simulation platform for an aviation monitoring memoire project. It is designed to demonstrate how secure delivery automation, auditability, and AI-assisted risk decisions can be integrated into a modern software pipeline.

## Runtime Layers

- React frontend renders the enterprise dashboard, monitoring pages, security views, logs, and DevSecOps pipeline visualization.
- Nginx serves the built frontend and proxies `/api` and Socket.io traffic to the backend in Docker.
- Express backend exposes protected REST APIs, manages authentication, persists audit/security data, and emits simulated realtime telemetry through Socket.io.
- FastAPI AI engine evaluates authentication, security, runtime, and pipeline events with an LLM (xAI Grok), bounded by a deterministic rule baseline, and returns risk score, risk level, explainability signals, and a recommended action.
- PostgreSQL stores demo users, logs, alerts, system status, audit events, AI events, and deployment states.
- Docker Compose starts the complete local environment.

## Security Model

- Passwords are hashed with bcrypt.
- API routes are protected with JWT middleware.
- Role checks protect administrative operations such as attack simulation.
- Helmet, CORS, rate limiting, and input validation are enabled in the backend.
- Login attempts are sent to the AI engine and stored in `ai_events`.
- High-risk authentication events can be rejected before token issuance.

## AI Risk Model

The AI engine sends the event to an LLM (xAI Grok) as untrusted data, validates the JSON answer, and keeps the higher of the LLM score and a deterministic rule-based score. If the LLM is unavailable, the rule-based score is returned with a `manual-review` action, so an outage never results in an approval. The rule baseline identifies signals such as:

- `authentication-abuse`
- `injection-attempt`
- `reconnaissance`
- `access-control`
- `critical-exposure`
- `runtime-degradation`
- `pipeline-warning`
- `failure-indicator`

The returned action is:

- `approve` for LOW/MEDIUM risk
- `manual-review` for HIGH risk
- `block` for CRITICAL risk

Decision thresholds are enforced by the application, not by the model, which keeps the gate explainable and testable.

## Simulation Model

Realtime events are generated by the backend every few seconds. Data is intentionally fake and safe for educational use. The platform simulates aviation monitoring modules, cybersecurity alerts, deployment targets, and container/service health.

## DevSecOps Context

The pipeline visualization models the target delivery flow: GitHub Webhooks, Jenkins, SonarQube, Trivy, OWASP ZAP, Docker Build, single-node k3s, and AWS EC2 deployment.

The Jenkinsfile enforces these gates:

- Backend, frontend, and AI engine unit tests run before analysis and deployment.
- The SonarQube Quality Gate aborts the pipeline when it fails.
- Trivy fails the build on fixable HIGH or CRITICAL image vulnerabilities.
- An OWASP ZAP baseline scan runs against an ephemeral Docker Compose test stack; FAIL-level findings block, WARN-level findings mark the build unstable.
- The AI security gate parses the AI engine's JSON decision and blocks critical risk.
- Images are pushed to Docker Hub and Nexus, deployed with Docker Compose, health-checked, and rolled out to a K3s cluster with `kubectl rollout status`.

## Current Constraints

- The frontend should be built with Node.js 20, matching the Dockerfile.
- Demo credentials are defined in `docker-compose.yml` and the K3s manifests; a production deployment should load them from Kubernetes Secrets or a secrets manager.
- The AI security gate currently sends a fixed pipeline event; feeding it the Trivy, ZAP, and SonarQube results is the next improvement.
